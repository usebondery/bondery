Every request needs one credential. Pick it from the work you are doing, not from the feature you want.

## Choose a credential

| You are building | Use | Read |
| --- | --- | --- |
| A script, cron job, CI step, or your own server | **API key** | [Use an API key](#1-api-key) |
| A call from a signed-in Bondery app session | **Session token** | [Use a session token](#2-session-token) |
| An AI assistant that works in your contacts | **MCP OAuth** | [Connect an AI assistant](#3-mcp-and-ai-assistants) |

Replace `https://api.usebondery.com` with your own API origin when you self-host. See [Self-hosting](../deploy/installation.mdx).

## 1. API key

An API key is a long-lived credential for unattended callers. It belongs to your account, and it keeps working until you delete it.

### Create a key

<Steps>
<Step>

Sign in at [app.usebondery.com](https://app.usebondery.com), or your own instance.

</Step>
<Step>

Open **Settings → API keys**.

</Step>
<Step>

Click **Create API key**. Choose a label, choose a permission level, then copy the key.

</Step>
</Steps>

<Callout type="warn">
The full key appears once. Store it in a secrets manager. Bondery keeps only a masked prefix for identification.
</Callout>

An account holds up to **5** keys. A deleted key stops working at once.

### Send the key

A key starts with `bondery_key_`. Send it as a bearer token on every request.

<PlatformCode
  posix={`curl "https://api.usebondery.com/contacts" \\
  -H "Authorization: Bearer bondery_key_<keyId>_<secret>"`}
  windows={`curl.exe "https://api.usebondery.com/contacts" -H "Authorization: Bearer bondery_key_<keyId>_<secret>"`}
/>

<Callout type="info">
**Running the API locally:** start Postgres and Redis, and set `BONDERY_PRIVATE_BETTER_AUTH_SECRETS`. See [Local development setup](../contributing/local-setup.mdx).
</Callout>

### Pick a permission level

The level is fixed when you create the key. Create a second key when you need a different level.

| Level | Allows | Use for |
| --- | --- | --- |
| **Read only** | `GET`, `HEAD` | Reporting, exports, read-only sync |
| **Full access** | Every method | Imports, creates, updates, deletes |

A read-only key that calls a write method receives **403** with `api_key_method_forbidden`. Create a full-access key instead of widening an old one.

## 2. Session token

A session token carries the identity of a person who just signed in. It suits first-party clients: the webapp, the mobile app, and the browser extension.

Session auth reaches **every** authenticated route, including settings, API key management, chat, and billing. An API key cannot.

### Get a token

Sign in through the app. The app then holds one of two credentials:

- a Better Auth session cookie, which the browser sends on its own
- an OAuth access token with the `api:access` scope, which you send as a bearer token

There is no public client registration for third-party apps. Use an [API key](#1-api-key) for your own integration.

### Send a token

<PlatformCode
  posix={`curl "https://api.usebondery.com/me/settings" \\
  -H "Authorization: Bearer YOUR_ACCESS_TOKEN"`}
  windows={`curl.exe "https://api.usebondery.com/me/settings" -H "Authorization: Bearer YOUR_ACCESS_TOKEN"`}
/>

A bearer token must be a real JWT. A malformed value never falls back to the session cookie.

## 3. MCP and AI assistants

AI assistants do not use either credential above. They connect to `POST /mcp` with **OAuth 2.1 and PKCE**, and they receive the `mcp:read` and `mcp:write` scopes.

An MCP token only calls MCP tools. It cannot call the REST API, and a REST API key cannot call `/mcp`. The two surfaces stay separate on purpose.

Connect a client, pick a consent level, and revoke access in **Settings → AI assistants**. The full walkthrough is in [Connect AI assistants](../bondery/mcp.mdx).

## Which routes accept which credential

API keys reach the integration routes only. Grouped by tag:

| Routes | API key | Session token |
| --- | --- | --- |
| Contacts: list, read, create, update, delete, select, by social handle, map pins, relationship graph, upcoming dates, vCard, groups, share preview | Yes | Yes |
| Contacts: import LinkedIn, Instagram, and vCard (parse and commit) | Yes | Yes |
| Contacts: share by email | Yes | Yes |
| Contacts: merge, merge recommendations, relationships, important dates, enrichment, enrichment queue, photo, keep-in-touch | No | Yes |
| Groups and tags, including membership | Yes | Yes |
| Interactions | Yes | Yes |
| Geocode: suggest, timezone | Yes | Yes |
| Account: profile, settings, session, photo, API keys, MCP consents, onboarding, feedback | No | Yes |
| Sync: bootstrap, pull, push, WebSocket ticket | No | Yes |
| Chat and chat sessions | No | Yes |
| Subscriptions: checkout, portal, sync | No | Yes |
| Browser extension internals | No | Yes |
| Health, mobile manifest, OAuth provider list, Stripe webhook | Neither | Neither |

A valid API key on a session-only route returns **403** with `api_key_route_forbidden`. When this table is not specific enough, open the route in the [API reference](./api-reference/index.mdx) and check its security badges.

## Errors

| HTTP | `code` | Cause |
| --- | --- | --- |
| `401` | `auth_required` | No credential on a protected route |
| `401` | `invalid_api_key` | Malformed key, wrong secret, or deleted key |
| `403` | `api_key_route_forbidden` | Valid key on a session-only route |
| `403` | `api_key_method_forbidden` | Read-only key used for a write |
| `409` | `api_key_limit_exceeded` | The account already holds 5 keys |

Every response also carries `agent_message`, which states the recovery step for an AI agent. See [Error codes](./errors/index.mdx) for the full catalog.

## Keep credentials safe

- Never commit a key or paste it into a public channel.
- Give each integration its own key, so you can delete one without breaking the others.
- Prefer **Read only** unless the integration writes.
- Rotate in three steps: create the new key, move the integration, delete the old key.
