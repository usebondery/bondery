## Principles

A Bondery secret is an ordinary environment variable with the `BONDERY_PRIVATE_*` prefix, plus `DATABASE_URL` for Postgres. Local development reads the root `.env.local` file. Production reads a secrets manager or the encrypted env store of your platform. Do not commit secrets, and do not send them in chat messages.

For which variables exist and what they do, see [Environment configuration](../contributing/environment.mdx) and [Authentication (contributors)](../contributing/auth.mdx).

1. **Generate once per environment.** Staging and production each get their own values. Never copy production secrets into local `.env.local`.
2. **Inject at runtime.** Containers and processes read secrets from the environment. Do not bake secrets into Docker images.
3. **Rotate on a schedule or on incident.** Document the blast radius before rotating. Some secrets invalidate all active sessions.
4. **Audit access.** Restrict who can read deploy env in Dokploy, AWS, or your vault. Prefer break-glass access over shared passwords.

## Where to store secrets

| Environment | Recommended approach |
| --- | --- |
| **Local dev** | Root `.env.local` (gitignored). Generate with `openssl rand -hex 32`. |
| **Self-host (Dokploy)** | Dokploy project **Environment** tab. Mark sensitive keys as secret. Same `BONDERY_*` names as [`deploy/bondery/.env.example`](../../deploy/bondery/.env.example). |
| **CI** | GitHub Actions **encrypted secrets** for deploy keys only. CI test Postgres uses ephemeral credentials in the workflow file, not production values. |
| **Cloud (optional)** | AWS Secrets Manager, GCP Secret Manager, or HashiCorp Vault. Sync into container env at deploy time through your orchestrator or an init sidecar. |

Bondery does not ship a custom secrets agent. Any store that can set process environment variables before `api` / `webapp` start is sufficient.

### Dokploy (current self-host path)

1. Open the Bondery stack project → **Environment**.
2. Paste `BONDERY_PRIVATE_*` values from a password manager or one-time generation.
3. Redeploy affected services. Env-only changes need no image rebuild.

Keep a **password manager record** per environment. List the secret names, the generation date, and the last rotation. Dokploy stores values but is not a full audit or rotation system.

### External secrets manager (larger installs)

Typical pattern:

```
Secrets Manager (AWS SM / Vault)
    → deploy hook or sidecar fetches JSON
    → exports BONDERY_PRIVATE_* before docker compose up
    → api / webapp containers inherit env
```

Store one JSON object per environment. Use keys that match the manifest canonical names. The `api` service `pre_start` init containers need the same OAuth and database secrets as the main API process. `release-migrate` provisions OAuth clients after `prisma migrate deploy`.

## Secret inventory

| Secret | Used by | Rotation impact |
| --- | --- | --- |
| `BONDERY_PRIVATE_BETTER_AUTH_SECRETS` | API | **Medium**. Versioned rotation avoids a mass logout when you add a new version first. Removing the last old version invalidates the sessions it still encrypts |
| `BONDERY_PRIVATE_WEBAPP_SESSION_SECRET` | Webapp | **High**. Invalidates all webapp session cookies |
| `BONDERY_PRIVATE_WEBAPP_OAUTH_CLIENT_SECRET` | API (hash), webapp (plaintext) | **Medium**. Update env on API and webapp, then re-run `provision-oauth-clients`. Users may need to log in again |
| `BONDERY_PRIVATE_API_KEY_PEPPER` | API | **High**. All existing API keys stop validating. Create new keys first |
| `BONDERY_PRIVATE_POSTGRES_PASSWORD` | DB, API | **High**. Requires a coordinated DB user password change, an env update, and a restart |
| `BONDERY_PRIVATE_AUTH_GITHUB_CLIENT_SECRET` | API | **Low**. Update the GitHub app and env. No user session impact |
| `BONDERY_PRIVATE_AUTH_LINKEDIN_CLIENT_SECRET` | API | **Low**. Same as GitHub |
| `BONDERY_PRIVATE_REDIS_URL` | API | **Medium**. May embed a password. Rotating Redis auth drops in-flight rate-limit state |

`BONDERY_PUBLIC_*` OAuth client ids are **not** secrets. Treat them like usernames. They are stable per environment and safe in config repos.

## Rotation runbooks

<a id="bondery_private_better_auth_secrets" />

### Better Auth signing secrets

`BONDERY_PRIVATE_BETTER_AUTH_SECRETS` holds the versioned signing keys for Better Auth. **Format:** `version:secret[,version:secret...]`. Put the highest version (the current signing key) first. Older decrypt-only versions follow.

**Bootstrap:**

<PlatformCode
  posix={`openssl rand -hex 32   # use as: BONDERY_PRIVATE_BETTER_AUTH_SECRETS=1:<value>`}
  windows={`$b = New-Object byte[] 32; [Security.Cryptography.RandomNumberGenerator]::Create().GetBytes($b); -join ($b | ForEach-Object { $_.ToString('x2') })   # use as: BONDERY_PRIVATE_BETTER_AUTH_SECRETS=1:<value>`}
/>

**When:** annual schedule, suspected compromise, or employee offboarding with deploy access.

**Zero-downtime rotation:**

1. Generate a new secret: `openssl rand -hex 32`.
2. Prepend it as a new version: `BONDERY_PRIVATE_BETTER_AUTH_SECRETS=2:<new>,1:<old>`.
3. Deploy `api`.
4. Wait for natural session refresh or re-login, or use a maintenance window.
5. Remove the old version: `BONDERY_PRIVATE_BETTER_AUTH_SECRETS=2:<new>`.

**Hard cutover (logs everyone out):** replace the entire value with a single new `1:<secret>` and redeploy.

**Verify:** `GET https://<api-domain>/status` and a test login on webapp + mobile. Record the rotation date in your password manager.

<a id="bondery_private_webapp_session_secret" />

### Webapp session secret

`BONDERY_PRIVATE_WEBAPP_SESSION_SECRET` encrypts the webapp's own session cookie. The value must be at least 32 characters.

**When:** annual schedule or webapp-only compromise suspicion.

1. Generate new value (`openssl rand -hex 32`).
2. Update **webapp** env only.
3. Redeploy webapp.
4. All users must log in again. API sessions and mobile tokens are unaffected.

<a id="bondery_private_webapp_oauth_client_secret" />

### Webapp OAuth client secret

`BONDERY_PRIVATE_WEBAPP_OAUTH_CLIENT_SECRET` is the shared secret between the API and the webapp. The API stores a hash. The webapp holds the plaintext value.

**When:** secret may have leaked from webapp env backup or logs.

1. Generate new secret (`openssl rand -hex 32`).
2. Update both API and webapp env (`BONDERY_PRIVATE_WEBAPP_OAUTH_CLIENT_SECRET`).
3. Redeploy `api`, or run `pnpm run provision-oauth-clients` against production. This updates the stored hash on the API.
4. Redeploy `api` and `webapp`.
5. Active webapp sessions may fail token refresh until users log in again.

<a id="bondery_private_api_key_pepper" />

### API key pepper

`BONDERY_PRIVATE_API_KEY_PEPPER` is mixed into every API key hash before storage. Keep this value stable. A change invalidates all existing keys.

**When:** pepper may have leaked. This is rare. Prefer creating new API keys over rotating pepper.

1. **Before** changing pepper, ask integrators to create new API keys in Settings.
2. Update pepper in API env.
3. Redeploy API.
4. Old keys return `401 invalid_api_key`. Delete old keys from the admin UI after integrators confirm migration.

<a id="bondery_private_postgres_password" />

### Postgres password

`BONDERY_PRIVATE_POSTGRES_PASSWORD` sets the Postgres user password. It feeds the `db` service and the derived `DATABASE_URL`.

**When:** database credential rotation policy.

1. `ALTER USER postgres PASSWORD '...'` inside Postgres, or recreate via compose on fresh installs only.
2. Update `BONDERY_PRIVATE_POSTGRES_PASSWORD` in deploy env. Compose rebuilds `DATABASE_URL` for services.
3. Restart `db` if needed, then `api`, and any job workers.
4. Verify migrations and a sample authenticated API call.

<a id="oauth-client-ids" />

### OAuth client ids

`BONDERY_PUBLIC_WEBAPP_OAUTH_CLIENT_ID` and `BONDERY_PUBLIC_OAUTH_CLIENT_ID` name the registered OAuth clients. They are public values, not secrets.

**When:** rarely. Only when you intentionally want new client registrations, for example an extension ID change in production.

1. Generate new ids if needed (secrets manager or `openssl rand -hex 16`).
2. Update env across affected apps.
3. Run provisioning (`api` redeploy or `pre_start`, or `pnpm run provision-oauth-clients -w api` manually).
4. Old refresh tokens for the previous client id will not work.

## First-time production setup

Generate all secrets before the first deploy:

<PlatformCode
  posix={`openssl rand -hex 32   # BONDERY_PRIVATE_BETTER_AUTH_SECRETS=1:<value>
openssl rand -hex 32   # BONDERY_PRIVATE_API_KEY_PEPPER
openssl rand -hex 32   # BONDERY_PRIVATE_WEBAPP_SESSION_SECRET
openssl rand -hex 32   # BONDERY_PRIVATE_WEBAPP_OAUTH_CLIENT_SECRET
openssl rand -hex 16   # BONDERY_PUBLIC_WEBAPP_OAUTH_CLIENT_ID
openssl rand -hex 16   # BONDERY_PUBLIC_OAUTH_CLIENT_ID
openssl rand -base64 24 | tr -d '/+=' | head -c 32   # BONDERY_PRIVATE_POSTGRES_PASSWORD`}
  windows={`# BONDERY_PRIVATE_BETTER_AUTH_SECRETS=1:<value>
$b = New-Object byte[] 32; [Security.Cryptography.RandomNumberGenerator]::Create().GetBytes($b); -join ($b | ForEach-Object { $_.ToString('x2') })
# BONDERY_PRIVATE_API_KEY_PEPPER
$b = New-Object byte[] 32; [Security.Cryptography.RandomNumberGenerator]::Create().GetBytes($b); -join ($b | ForEach-Object { $_.ToString('x2') })
# BONDERY_PRIVATE_WEBAPP_SESSION_SECRET
$b = New-Object byte[] 32; [Security.Cryptography.RandomNumberGenerator]::Create().GetBytes($b); -join ($b | ForEach-Object { $_.ToString('x2') })
# BONDERY_PRIVATE_WEBAPP_OAUTH_CLIENT_SECRET
$b = New-Object byte[] 32; [Security.Cryptography.RandomNumberGenerator]::Create().GetBytes($b); -join ($b | ForEach-Object { $_.ToString('x2') })
# BONDERY_PUBLIC_WEBAPP_OAUTH_CLIENT_ID
$b = New-Object byte[] 16; [Security.Cryptography.RandomNumberGenerator]::Create().GetBytes($b); -join ($b | ForEach-Object { $_.ToString('x2') })
# BONDERY_PUBLIC_OAUTH_CLIENT_ID
$b = New-Object byte[] 16; [Security.Cryptography.RandomNumberGenerator]::Create().GetBytes($b); -join ($b | ForEach-Object { $_.ToString('x2') })
# BONDERY_PRIVATE_POSTGRES_PASSWORD
$c = New-Object byte[] 32; [Security.Cryptography.RandomNumberGenerator]::Create().GetBytes($c); -join ($c | ForEach-Object { '0123456789abcdefghijklmnopqrstuvwxyzABCDEFGHIJKLMNOPQRSTUVWXYZ'[$_ % 62] })`}
/>

Each Windows line prints one value. The last line prints a 32-character alphanumeric password, which replaces the `tr` and `head` pipeline.

Store them in your secrets manager, map into [`deploy/bondery/.env`](../../deploy/bondery/.env.example), then deploy. The `api` service `pre_start` runs `release-migrate`, which applies schema migrations and provisions OAuth clients automatically.
