## Schema migrations


The `api` service's `pre_start` init containers apply `prisma migrate deploy`, `functions.sql`, OAuth provisioning, and S3 bucket bootstrap **before** the main API container starts.

`pre_start` runs when the API service is created or recreated — for example after pulling a new image tag, changing the init definition, or an explicit `docker compose up` that recreates `api`. Compose **skips** unchanged `pre_start` steps on ordinary container restarts. There is no separate `migrate` service.

Requires Docker Compose **v2.38+**.

## Image upgrades

Both services run the image version that [`docker-compose.yml`](../../deploy/bondery/docker-compose.yml) names by default. Each release stamps its own version there, so the compose file of release `vX.Y.Z` runs `api` and `webapp` at `X.Y.Z`. The two images always move together. To upgrade, fetch the compose files of the new release (check out its `vX.Y.Z` tag), then pull and start:

<PlatformCode
  posix={`./scripts/upgrade.sh`}
  windows={`docker compose pull api webapp
docker compose up -d`}
/>

This pulls the `api`/`webapp` images that the compose file names and runs `docker compose up -d`. On Windows, run the two `docker compose` commands from `deploy/bondery`. When the `api` image changes, Compose recreates `api` and re-runs `pre_start`.

### Pinning a version

Set `BONDERY_INFRA_VERSION` to run a version other than the one in your compose file, for example a rollback target (it pins **both** api and webapp):

<PlatformCode
  posix={`BONDERY_INFRA_VERSION=1.7.4 docker compose up -d api webapp`}
  windows={`$env:BONDERY_INFRA_VERSION = "1.7.4"
docker compose up -d api webapp`}
/>

Always redeploy api and webapp together when changing the version pin.
