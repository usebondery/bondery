# ADR 0005: API pre_start bootstrap

## Status

Accepted (2026-07-29)

## Context

Self-host `docker compose up` must bring a greenfield stack to a working state without manual host tooling (AWS CLI, repo checkout, `tsx` scripts). Today:

- Prisma migrations, SQL functions, OAuth client provisioning, and platform admin promotion run only via manual steps or CI `release-migrate`.
- SeaweedFS S3 buckets (`avatars`, `linkedin-logos`) are created by a host script requiring AWS CLI.
- Documentation incorrectly references a separate `migrate` Compose service that does not exist.

The production API image ships compiled `apps/api/dist` and `packages/` only — no `tsx`, no `apps/api/scripts/`. Any bootstrap logic must run as compiled Node entrypoints inside the API image.

## Decision

1. **Unified `api.pre_start`** (Docker Compose v2.38+) runs two init containers before the main API container, in order:
   - `node apps/api/dist/cli/release-migrate.js` — `prisma migrate deploy`, `functions.sql`, OAuth clients, platform admins
   - `node apps/api/dist/cli/ensure-storage-buckets.js` — create required S3 buckets if missing

2. **Main API process** handles runtime concerns in `buildServer()` before `listen()`:
   - Env validation → `buildServer()` (`initializeRuntime()` for Postgres, storage, SMTP, Redis, pg-boss → rate-limit → `registerAuthRoutes()` → `verifyAuthRuntime()` via `fastify.inject('/auth/jwks')`) → `listen()`

3. **No separate `migrate` Compose service** — upgrades re-run `pre_start` when the API image or init definition changes.

4. **Host-run dev** (`pnpm run dev`) calls the same bootstrap helpers before `buildServer()` when `NODE_ENV=development`. Optional `BONDERY_DEV_*` flags (see environment docs) — never used in Compose.

5. **`/health/ready` storage probe** (phase 2) adds `HeadBucket` on required buckets — probe only, never create buckets from health checks.

## S3 readiness vs bootstrap vs boot verify

Three layers, analogous to Postgres (`pg_isready` ≠ migrate ≠ `SELECT 1`):

1. **Compose `seaweedfs-s3` healthcheck** — unsigned ListBuckets (`GET /` on port 8333). HTTP 200 with `ListAllMyBucketsResult` or HTTP 403 with S3 `Error` XML means the gateway speaks S3. Empty `GET /status` 200 is process liveness, not S3 readiness. `depends_on: seaweedfs-s3: service_healthy` is only valid with this S3-speaking probe.

2. **`pre_start` `ensure-storage-buckets`** (and host-run `pnpm run dev`) — signed HeadBucket wait-then-act. CreateBucket only after HeadBucket classifies the bucket as missing (404 / NotFound / NoSuchBucket). Public-read PutBucketPolicy after the bucket exists.

| HeadBucket | Action |
|---|---|
| 200 | exists; PutBucketPolicy |
| 404 / NotFound / NoSuchBucket | CreateBucket (`BucketAlreadyOwnedByYou` / `BucketAlreadyExists` = success), then policy |
| 403 (`httpStatusCode` or `AccessDenied`) | Fail immediately. Do not retry. Do not create. |
| UnknownError, timeout, unreachable, 5xx | Retry HeadBucket only. Never create. Exhaust budget → fail. |

3. **`initObjectStorage` and `GET /health/ready`** — one fail-fast signed HeadBucket pass on required buckets. No retries, no SeaweedFS `/status`, never create.

Compose `pre_start` runs when the API service is created, not on ordinary container restarts. If `initObjectStorage` fails and Compose `restart: unless-stopped` brings the main process back, bootstrap does not re-run — recreate the API service rather than looping restarts. Do not change the restart policy to paper over that.

## Why JWKS stays in the main process

`verifyAuthRuntime()` runs inside `buildServer()` after auth routes are mounted and **before** `listen()`. It calls `fastify.inject({ method: 'GET', url: '/auth/jwks' })` — same integration coverage as an HTTP probe, but in-process (no loopback socket, no Traefik/DNS hairpin to `BONDERY_PUBLIC_API_URL`). The public issuer URL is still logged for operators. Running this in `pre_start` is circular (no Fastify app yet); folding it into `initializeRuntime()` is the wrong seam (infra deps vs in-process auth wiring).

## Why not pre_start on seaweedfs-s3

`pre_start` runs before the service starts — it cannot wait for the S3 gateway healthcheck. The API service already `depends_on: seaweedfs-s3: service_healthy`.

## Consequences

- **Positive:** One `docker compose up -d` for greenfield self-host; no AWS CLI on the host; idempotent deploy pipeline; single image for app + bootstrap.
- **Positive:** `webapp` remains gated on `api: service_healthy` — init completes before HTTP traffic.
- **Trade-off:** Requires Docker Compose v2.38+ (`pre_start` support).
- **Trade-off:** API image must ship compiled CLI entrypoints and `packages/db/prisma` migrations.
- **Out of scope:** pg-boss worker wiring; JWKS check in `pre_start`; legacy Compose fallback files.
