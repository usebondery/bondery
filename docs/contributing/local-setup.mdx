Follow the dependency chain: **Postgres → Redis → Mailpit → (optional) SeaweedFS → API → apps**. Each service reads from the one before it, so start them in that order.

**Local web URLs** use [Portless](https://github.com/vercel-labs/portless) HTTPS. `scripts/dev/portless-alias.mjs` registers every hostname as a static alias (hostnames and ports come from `packages/schemas/src/constants/dev-ports.ts`). Open these in the browser:

| App | Local URL |
|---|---|
| website | [https://usebondery.test](https://usebondery.test) |
| webapp | [https://app.usebondery.test](https://app.usebondery.test) |
| api | [https://api.usebondery.test](https://api.usebondery.test) |
| Mailpit UI | [https://mail.usebondery.test](https://mail.usebondery.test) |

Apps still listen on fixed loopback ports behind the proxy: website `26630`, webapp `26632`, and the API `26642`. The API serves **HTTPS only**, like the deployed stack: Portless forwards to it over HTTPS, the webapp's server side calls `https://127.0.0.1:26642` and trusts the dev API CA, and a phone reaches it through `tailscale serve` (see the mobile section). It has no plain HTTP port. `dev:classic` serves the webapp and website on their loopback ports. Do not open raw `http://localhost:2663x` for daily web work.

Aliases use `PORTLESS_TLD=test` and are stored with `pid 0`, so they survive a dev server restart and the hosts file stays complete. Each app's `dev` script re-registers its own alias, then starts the server. Mailpit SMTP stays on `127.0.0.1:26640` (not Portless).

Portless only manages the hostnames in `~/.portless/routes.json`. If a hostname does not resolve, run `node scripts/dev/portless-alias.mjs` from the repo root, then `pnpm exec portless hosts sync` from the repo root in an **elevated** shell (Windows needs Administrator to write the hosts file).

**Environment variables:** edit root `.env.local` once, then sync — see [Environment configuration](environment.mdx).

```bash
pnpm install
pnpm run setup:dev
# edit .env.local (OAuth / optional integrations)
pnpm run start:postgres
pnpm run start:redis
pnpm run start:mailpit
pnpm run start:seaweedfs   # required for avatar / logo uploads
pnpm run env
pnpm run dev:webapp-api    # API + webapp via Portless HTTPS
```

On first API start in development, `runDevelopmentBootstrap()` runs the same pipeline as production `api.pre_start` (migrations, SQL functions, OAuth clients, platform admins, storage buckets) unless you set `BONDERY_DEV_SKIP_RELEASE_MIGRATE` or `BONDERY_DEV_SKIP_STORAGE_BUCKETS`. You do **not** need to run `db:migrate:deploy` and `provision:oauth-clients` manually before every `pnpm run dev`.

## Prerequisites

| Tool | Version | Notes |
|---|---|---|
| [Node.js](https://nodejs.org/) | 26 | Declared in root `package.json` `devEngines.runtime` (pnpm downloads on install); `.nvmrc` is optional for `nvm use` / `fnm use` |

| [Docker](https://www.docker.com/) | latest | Local Postgres, Redis, Mailpit, and SeaweedFS |

For mobile development you also need Expo tooling (installed via root `pnpm install`) and a native toolchain: **iOS** — Xcode + Simulator or a physical device; **Android** — Android Studio + emulator or USB debugging.

## Postgres database

The local Postgres instance is the foundation everything else connects to. Start it before running the API.

### Environment variables

Set `BONDERY_PRIVATE_POSTGRES_PASSWORD` in root `.env.local` (`pnpm run env` derives `DATABASE_URL` into api/db). See [`.env.local.example`](../../.env.local.example). OAuth client ids/secrets for Better Auth live under `BONDERY_PRIVATE_AUTH_*`. After editing, run `pnpm run env` to sync app env files.

> **No OAuth credentials yet?** The stack will still start — email-based flows may be limited, but you can develop against the API. Social login buttons need GitHub/LinkedIn app credentials.

### Start Postgres

From the repo root (reads `BONDERY_PRIVATE_POSTGRES_PASSWORD` from `.env.local`):

```bash
pnpm run start:postgres
```

Postgres listens on **host port 54322**, loopback only. `pnpm run env` writes `DATABASE_URL` to api/db using `BONDERY_PRIVATE_POSTGRES_PASSWORD` from root `.env.local`.

Local Postgres is set up like the deployed one: TLS only, plaintext connections are refused. `start:postgres` first creates a private CA and a server certificate in `.temp/postgres-secrets` (git-ignored), then starts Postgres. It keeps existing certificates. The API, Prisma, and pg-boss trust the CA through these lines in root `.env.local` (`pnpm run setup:dev` adds them):

```bash
DATABASE_SSL_MODE="verify-full"
DATABASE_SSL_ROOT_CERT_FILE="../../.temp/postgres-secrets/client/ca.crt"
```

Connect with psql the same way:

```bash
psql "host=localhost port=54322 dbname=bondery user=postgres sslmode=verify-full sslrootcert=.temp/postgres-secrets/client/ca.crt"
```

An older dev database ran without TLS. Run `pnpm run setup:dev` once, then `pnpm run env` and `pnpm run start:postgres`; your data stays.

Stop with `pnpm run stop:postgres`.

### Migrations (manual / one-off)

The API dev server runs migrations on boot. Use these when you author schema changes or need a clean reset:

| Command | Description |
|---|---|
| `pnpm run db:migrate:deploy` | Apply pending Prisma migrations |
| `pnpm run db:migrate:dev` | Author new migrations interactively (requires shadow DB with PostGIS) |
| `pnpm run db:studio` | Open Prisma Studio against `DATABASE_URL` |
| `pnpm run db:functions` | Apply raw SQL functions (included in dev bootstrap) |
| `pnpm run provision:oauth-clients` | Upsert first-party OAuth clients (included in dev bootstrap) |

For a full auth walkthrough, see [Authentication](./auth.mdx).

### Mobile sync (Postgres changelog)

Mobile offline sync uses **custom pull/bootstrap** endpoints on the API (`GET /sync/bootstrap`, `GET /sync/pull`) backed by `sync_change_log`. No separate sync service is required beyond Postgres + API.

## Object storage (SeaweedFS)

Contact **avatars** and cached **LinkedIn logos** use the S3-compatible SeaweedFS gateway. Credentials live **only** in root `.env.local` (`BONDERY_PRIVATE_S3_ACCESS_KEY_ID` / `SECRET`); the `seaweedfs-s3` container renders its config from those vars at startup.

```bash
pnpm run start:seaweedfs          # S3 API on https://127.0.0.1:8443, public reads on http://127.0.0.1:8333
pnpm run setup:seaweedfs      # optional — API dev boot also ensures buckets
```

Local SeaweedFS is set up like the deployed one: the nodes talk to each other over mutual TLS, and the API uses HTTPS. `start:seaweedfs` first creates a private storage CA and a cluster certificate in `.temp/storage-secrets` (git-ignored), then starts the cluster. It keeps existing certificates. Browsers load public objects over plain HTTP on `8333`, like Traefik does in production.

Optional smoke. Use `curl.exe` on Windows, because PowerShell aliases `curl` to `Invoke-WebRequest`:

<PlatformCode
  posix={`curl -sS -D- --cacert .temp/storage-secrets/client/ca.crt https://127.0.0.1:8443/
curl -sS -D- http://127.0.0.1:8333/`}
  windows={`curl.exe -sS -D- --cacert .temp/storage-secrets/client/ca.crt https://127.0.0.1:8443/
curl.exe -sS -D- http://127.0.0.1:8333/`}
/>

Expect HTTP 403 and S3 `Error` XML from both commands. Empty 200 on `/status` is not sufficient.

Stop with `pnpm run stop:seaweedfs`.

Set in `.env.local` (see `.env.local.example`; `pnpm run setup:dev` adds the last two):

```text
BONDERY_PUBLIC_STORAGE_URL=http://127.0.0.1:8333
BONDERY_PRIVATE_S3_ENDPOINT=https://127.0.0.1:8443
BONDERY_PRIVATE_S3_TLS_CA_FILE=../../.temp/storage-secrets/client/ca.crt
```

An older setup used `http://127.0.0.1:8333` for the API. Run `pnpm run setup:dev` once, then `pnpm run env`, `pnpm run stop:seaweedfs`, and `pnpm run start:seaweedfs`; your files stay.

<Callout type="warn">
**Avatar previews need public bucket policy.** Setup applies anonymous `GetObject` on `avatars`. If uploads succeed but images 404/403 in the browser, run `pnpm run setup:seaweedfs` or restart the API (dev bootstrap).
</Callout>

<Callout type="info">
**`linkedin-logos` bucket:** stores company/school logos fetched during LinkedIn import (`{userId}/{linkedinId}.jpg`). Created alongside `avatars` by `ensure-storage-buckets` on API startup.
</Callout>

## API server (`apps/api`)

### Environment variables

Prefer root `.env.local` + `pnpm run env` (see [Environment configuration](environment.mdx)). That writes `apps/api/.env.development.local`.

Required secrets include `BONDERY_PRIVATE_BETTER_AUTH_SECRETS` (format `1:<secret>`, each secret ≥32 characters) and `BONDERY_PRIVATE_API_KEY_PEPPER` — see [API keys](#api-keys-long-lived-integration-tokens) below.

For mobile sync, set CORS for Expo web if needed:

```text
BONDERY_PUBLIC_EXTRA_ALLOWED_ORIGINS=http://localhost:26634
```

#### Redis

Redis powers **rate limiting**, **Better Auth secondary storage** (`bondery:auth:*`), **mobile sync wake** (pub/sub), and **WebSocket ticket** storage in the API. **Required** for local API development.

| Mode | `BONDERY_PRIVATE_REDIS_URL` | When to use |
|------|---------------------|-------------|
| **Local Docker (required)** | `rediss://127.0.0.1:26636` | Normal local API work |

Local Redis is set up like the deployed one: TLS only, with a password. From the repo root (Docker must be running):

```bash
pnpm run start:redis
```

`start:redis` first creates a random password and a TLS certificate in `.temp/redis-secrets` (git-ignored), then starts Redis on `127.0.0.1:26636`. It keeps existing secrets. Run it again after you delete that folder.

Stop with `pnpm run stop:redis`. Verify:

```bash
docker exec bondery-redis sh -c 'REDISCLI_AUTH="$(cat /bondery-redis/client/password)" redis-cli --tls --cacert /bondery-redis/client/ca.crt -h localhost ping'
```

The answer is `PONG`.

Wire the API in `apps/api/.env.development.local`. `pnpm run setup:dev` writes these values into root `.env.local`, and `pnpm run env` copies them. The two paths are relative to `apps/api`:

```text
BONDERY_PRIVATE_REDIS_URL="rediss://127.0.0.1:26636"
BONDERY_PRIVATE_REDIS_PASSWORD_FILE="../../.temp/redis-secrets/client/password"
BONDERY_PRIVATE_REDIS_TLS_CA_FILE="../../.temp/redis-secrets/client/ca.crt"
```

An older `.env.local` still has `redis://127.0.0.1:26636`. Run `pnpm run setup:dev` once to update it, then `pnpm run env`.

`BONDERY_PRIVATE_REDIS_URL` is **required** in development and production. See [Installation](../deploy/installation.mdx).

#### Mailpit (local SMTP)

The API verifies SMTP at boot. Local development must send through **Mailpit** on loopback — not ProtonMail or Plunk. Production and Dokploy stay on Plunk.

| Mode | Host / port | When to use |
|------|-------------|-------------|
| **Local Docker (required)** | `127.0.0.1:26640` | Normal local API work |

From the repo root (Docker must be running):

```bash
pnpm run start:mailpit
```

Stop with `pnpm run stop:mailpit`. Human UI: [https://mail.usebondery.test](https://mail.usebondery.test) (Portless alias). Loopback UI/API for e2e stays [http://127.0.0.1:26641](http://127.0.0.1:26641).

Wire the API in root `.env.local` (then `pnpm run env`):

```text
BONDERY_PRIVATE_EMAIL_HOST=127.0.0.1
BONDERY_PRIVATE_EMAIL_PORT=26640
BONDERY_PRIVATE_EMAIL_USER=mailpit
BONDERY_PRIVATE_EMAIL_PASS=mailpit
```

If SMTP host is not loopback (`127.0.0.1` / `localhost`), the development API **refuses to boot**. Start Mailpit first.

<Callout type="warn">
**Infisical `env:pull`:** set the **development** Infisical `BONDERY_PRIVATE_EMAIL_*` values to Mailpit (`127.0.0.1:26640`, any user/pass). Staging and production stay on Plunk. If development Infisical still has ProtonMail, the next `pnpm run env:pull` restores that host and API boot fails on purpose.
</Callout>

#### API keys (long-lived integration tokens)

| Variable | Purpose |
|---|---|
| `BONDERY_PRIVATE_API_KEY_PEPPER` | Server secret mixed into API key hashes before storage. Use a random value **at least 32 characters** (e.g. `openssl rand -hex 32`). |

Validated API keys resolve directly to a `userId` in application code — no JWT minting step. See [API authentication](../api/authentication.mdx).

Keep `BONDERY_PRIVATE_API_KEY_PEPPER` stable. If you change it after creating keys, existing keys stop working — create new keys after rotating the pepper.

### Start

First Portless trust (once per machine): from the repo root, run `pnpm exec portless trust`. `portless` is a devDependency of the workspace root, so run it from there. On Windows, run it from an elevated PowerShell so Portless can write hosts, or run `pnpm exec portless hosts sync`.

```bash
cd apps/api
pnpm run dev
```

`dev` registers the API alias, then starts the server on `https://127.0.0.1:26642`, with the certificate that `pnpm run api:secrets` creates. Open [https://api.usebondery.test](https://api.usebondery.test). The API binds loopback only in development; set `API_HOST=0.0.0.0` only when something outside this machine's loopback must reach it (for example Tailscale on the Windows host with the API in WSL2).

## Mobile application (`apps/mobile`)

Run the mobile app against your local API and Postgres stack. Requires Postgres migrations and a running API first.

### Environment variables

Filled by `pnpm run env` into `apps/mobile/.env.local` (`BONDERY_PUBLIC_*`). Expo loads those into `app.config.ts` `extra`.

#### Phone, simulator, or emulator over Tailscale

The API serves HTTPS only, with a certificate from the private dev CA. A phone or an emulator can neither resolve `api.usebondery.test` nor trust that CA, so the mobile app reaches the API through `tailscale serve`, which gives it a name with a public certificate on your tailnet.

1. Install Tailscale on your dev machine and on the phone, and sign in to the same tailnet. In the Tailscale admin console, on the DNS page, turn on **MagicDNS** and **HTTPS Certificates**.
2. Publish the API and store its URL:

   ```bash
   pnpm run dev:mobile-api
   ```

   It runs `tailscale serve` for `https://<machine>.<tailnet>.ts.net:26642`, which forwards to the API on loopback, and writes that URL to `BONDERY_DEV_MOBILE_API_URL` in `.env.local`.
3. Run `pnpm run env`. The mobile app gets the Tailscale URL as its API URL; the webapp and the API keep `https://api.usebondery.test`, so web development keeps working at the same time.
4. Start the app (below). Stop publishing with `pnpm run dev:mobile-api -- --off`, then `pnpm run env`.

Start Metro with LAN binding so the phone can load the JS bundle over Tailscale:

```bash
cd apps/mobile
pnpm exec expo start --host lan
```

**Social sign-in on a phone.** OAuth providers redirect to the API's own URL. To test GitHub or LinkedIn sign-in on a phone, set `BONDERY_PUBLIC_API_URL` in `.env.local` to the Tailscale URL as well, register `https://<machine>.<tailnet>.ts.net:26642/auth/callback/github` in your OAuth app, run `pnpm run env`, and restart the API. Switch back to `https://api.usebondery.test` for web development.

**WSL2:** With Tailscale on the Windows host and the API in WSL2, set `API_HOST=0.0.0.0` in `.env.local`, so the Windows side can reach the API.

#### Android emulator note

On Android emulators, `127.0.0.1` and `localhost` in the other mobile URLs (public storage reads, webapp, website) are **automatically rewritten** to `10.0.2.2` (the host loopback from the emulator). The API URL is the Tailscale URL above; the emulator resolves it through the host when Tailscale runs there.

### Start

**Option A — API + mobile from repo root:**

```bash
pnpm run dev:mobile
```

**Option B — mobile only** (with Postgres and API already running):

```bash
cd apps/mobile
pnpm run dev
```

Then press `i` for iOS Simulator, `a` for Android emulator, or scan the QR code with Expo Go / a dev client.

#### Native dev builds

For SQLite sync and background tasks, use a development build instead of Expo Go:

```bash
cd apps/mobile
pnpm run dev:prebuild    # regenerates android/ and ios/ — only when native deps change
pnpm run android:dev     # USB device or emulator
pnpm run ios             # iOS Simulator or device
```

On Windows, Gradle reads `JAVA_HOME`. Expo Android builds need **JDK 17**. A User `JAVA_HOME` that points at a removed JDK, or at JDK 25, overrides a valid Machine JDK 17, and the native build fails before install.

`jdk-17.0.20.8-hotspot` is OpenJDK **17** (patch 20.8), not Java 20.

`pnpm run android:dev` replaces a missing, stale, or non-17 `JAVA_HOME` with a Microsoft JDK 17 or Android Studio JBR. Open a **new** terminal after you change User env vars. The current terminal keeps the old value.

To persist the User value:

1. Open Environment Variables (Settings → System → About → Advanced system settings).
2. Set User `JAVA_HOME` to the folder that contains `bin\java.exe`.
3. Example: `C:\Program Files\Microsoft\jdk-17.0.20.8-hotspot`.
4. Open a new terminal.

### Verify sync

1. Sign in with GitHub or LinkedIn (same providers as the webapp).
2. Wait for the initial sync banner to clear — contacts should match your account.
3. Toggle airplane mode, edit a contact, then reconnect — changes should drain from the outbox and appear on web.

If sync requests return **426**, protocol or SQLite schema versions are mismatched — rebuild the app after pulling API/mobile changes.

If bootstrap or pull return **401**, confirm the mobile session token matches your local API and Better Auth configuration.

See also [Sync architecture (mobile)](sync-architecture.mdx) and [apps/mobile/README.md](../../apps/mobile).

## Running everything at once

> **Before using these commands**, complete environment setup in the steps above.

From the repo root:

```bash
# 1. Infrastructure
pnpm run start:postgres
pnpm run start:redis
pnpm run start:mailpit
pnpm run start:seaweedfs

# 2. App dev
pnpm run env
pnpm run dev:webapp-api

# Or: api + webapp + website + chrome-extension
pnpm run dev:extension

# Or: api + mobile
pnpm run dev:mobile
```

These scripts are defined in the root `package.json` and orchestrated by Turborepo (`turbo run`). Persistent app processes (`next dev`, and the API under `node --watch`) stay up; package `tsc --watch` runs beside them. Do not wrap those servers in `turbo watch` — that kills Next on any tracked file write. Locale JSON is copied by `@bondery/translations#dev` (poll + `fs.watch`); refresh the tab to see new copy. The API restarts once per save burst when the locale watch stamp changes.

### Stripe billing (optional)

Inbound Stripe events (portal cancel, payment failure, trial-ending email) do not reach your laptop without the CLI. After [Stripe CLI](https://docs.stripe.com/stripe-cli) is installed and Portless is trusted (`pnpm exec portless trust`):

```bash
stripe login                 # once per machine — not run by our scripts
pnpm run setup:stripe        # write CLI webhook secret → .env.local → pnpm run env
# restart the API under Portless (`pnpm run dev` / `dev:webapp-api`)
pnpm run dev:stripe          # second terminal: forward to https://api.usebondery.test/webhooks/stripe
```

See [Environment configuration](environment.mdx#stripe-cli-local-webhooks).

### Production builds

```bash
pnpm exec turbo build --filter=api
pnpm exec turbo build --filter=webapp
pnpm exec turbo build --filter=website
pnpm exec turbo build --filter=chrome-extension
```

Shortcuts: `pnpm run build`, `pnpm run build:api`, `build:webapp`, `build:website`.

### Local dev watch

```bash
pnpm run dev                    # turbo run dev — all apps with a dev script
pnpm run dev:webapp-api         # webapp + api (usual local stack)
pnpm run dev:api                # api only
pnpm run dev:webapp             # webapp only
pnpm run dev:mobile             # api + mobile
pnpm run dev:emails             # React Email preview only (port 26639)
pnpm run build:packages       # one-shot package compile
```

Lint the whole repo from the root: `pnpm run lint` (Biome).
